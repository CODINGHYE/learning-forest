# 개발 하네스 운영 규칙

## 기준과 책임

사용자는 학습 목표와 완료 조건을 정한다. 개발자는 구현·검증·문서 정합성을 한 변경으로 관리한다. AI도 같은 절차를 따른다. 대화에서 합의한 지속적인 결정은 관련 설계나 작업 계획에 남긴다.

| 정보 | 수정할 원본 | 파생 결과 |
|---|---|---|
| 질문 ID·제목·개념 이름·기본 개념 설명·용도·목표·예상·실험 설명·근거·다음 질문·의미 관계 표, 큰 질문 제목·소개 | [QUESTION_SCENARIOS](QUESTION_SCENARIOS.md) | `learning-forest/dist/content.js` |
| 한 줄 요약·조작 안내·범례·용어 풀이·이동 안내 | `learning-forest/content/review.json` | `content.js`의 `review` |
| 그룹 짧은 이름·대표 질문, 생성 규칙 | `learning-forest/scripts/build_content.py` | `content.js` |
| 수치·렌더링·화면 제어 | `dist/math.js`, `dist/scene.js`, `dist/app.js`, HTML/CSS | 실행 화면 |
| PDF 본문 추출·AI 결과 검사 | `pdf_analysis.py`, `server.py` | 업로드 문서의 임시 지도 |
| 현재 기능 상태·확인 범위 | [STATUS](STATUS.md) | 완료 보고 |

`review.json`에 별도 `explain`·`predict`를 두지 않는다. 기본 개념 설명·용도는 설계서의 해당 필드, 선택형 실험 설명은 질문별 인용문, 의미 연결은 관계 표를 수정한 뒤 생성기를 실행한다. `content.js`를 직접 고쳐도 검증에서 원본 불일치로 실패한다. 생성기는 안정적인 질문 ID, 필수 필드, 끊어진 질문 연결도 검사한다.

## 변경 절차

1. `AGENTS.md`에서 필요한 기준 문서를 찾는다.
2. 작은 변경은 목표·완료 조건을 작업 설명에 쓴다. 여러 단계가 필요한 변경은 [계획 양식](plans/TEMPLATE.md)을 복사해 `docs/plans/`에 기록한다.
3. `codex/주제` 브랜치에서 작업한다. 질문 표현과 동작을 바꾸면 설계와 원본을 함께 수정한다.
4. 설명 변경 뒤에는 `python learning-forest/scripts/build_content.py`로 생성하고 diff를 확인한다. Python 경로는 환경에 맞게 사용한다.
5. `verify.ps1`로 전체 검증한다. 빠른 검증만 실행했다면 브라우저 미확인을 명시한다.
6. 실패 원인을 수정하고 필요한 회귀 검사를 추가한다. 확인된 오류는 원칙 문서의 CM 기록에 재현·원인·수정·확인을 남긴다.
7. 상태 문서와 작업 결과를 갱신하고 커밋한다. 문서를 포함한 검증 입력이 바뀌었으면 최종 상태에서 다시 검증한다.

## 검증 계약

| 단계 | 검사 범위 | 실패 시 |
|---|---|---|
| repository | 관리 문서 존재·로컬 파일 링크·중첩 Git·추적된 환경 파일 | 저장소와 문서 정리 |
| content | 13개 질문 ID·설명·출처·연결·생성 파일 최신성 | 원본 수정 후 명시적으로 재생성 |
| syntax | 브라우저 JavaScript 파싱 | 구문 수정 |
| math | 독립 수치 기준과 자동미분 교차 확인 | 계산과 설명 함께 확인 |
| python | PDF 처리·근거 검증·로컬 HTTP·API 모의 실패 | 해당 경계 수정 |
| browser | PDF 전용 흐름·13개 선택형 실험·카메라·재생·5개 화면 폭·실패/복구·메모·빈 상태 | 화면 흐름 수정 |
| unchanged-inputs | 검증 도중 입력 변경 여부 | 안정된 상태에서 재실행 |

전체 모드의 어느 단계든 실패하면 종료 코드 1, 결과 `failed`다. 빠른 모드는 성공해도 `partial`이며 브라우저 검증을 대신하지 않는다. 브라우저나 의존성이 없으면 전체 검증은 실패하고 필요한 설정을 알린다. 실패를 자동 건너뛰지 않는다.

Python 테스트의 생략 개수도 기록한다. 기본 검증은 합성 PDF를 사용하며 개인 다운로드 폴더나 교재를 요구하지 않는다. 교재 원본 검사는 `scripts/check_reference_pdf.py`에 경로와 기대 개수를 명시해 별도로 수행한다. 테스트가 생략된 전체 실행은 `partial`과 종료 코드 2로 남긴다. 빠른 모드가 정상 종료한 경우만 `partial`이어도 종료 코드 0이다.

`qa-output/verification.json`은 HEAD, 작업 트리 상태, 입력 SHA-256, 런타임 버전, 단계별 성공·실패, UTC 실행 시각을 기록한다. 입력 해시는 Git 텍스트 정규화에 맞춰 CRLF를 LF로 바꾼 실제 소스 내용으로 계산한다. 생성물·자료·비밀값은 포함하지 않는다. 과거 `report.json`은 이전 화면에 대한 기록이며 현재 결과로 재사용하지 않는다.

검증은 별도 포트의 서버를 사용하고 API 키를 비운 환경에서 실행한다. HTTP와 UI 검사는 로컬 서버에만 요청하고, OpenAI 호출은 모의 응답으로 검사한다. 실제 API 연동·비용·생성 품질은 별도 검증으로 남긴다.

검증 프로세스끼리는 파일 잠금으로 동시 실행을 막는다. 이미 검증이 진행 중이면 새 실행은 기존 증거를 덮어쓰지 않고 실패한다. 테스트 서버는 운영체제가 배정한 포트에 먼저 바인딩한 뒤 실행 ID와 PID를 확인하므로 사용자의 미리보기 서버에 붙지 않는다.

## 완료 판단

보고할 때 설계 반영, 코드 구현, 자동 검증, 사람의 화면 검토, 학습자 이해 확인을 각각 적는다. 자동 검증 성공으로 학습 효과나 화면 읽기 도구 사용성을 완료 처리하지 않는다. 배포·외부 접속 검증은 현재 보류되어 있다.

여러 작업이 같은 파일을 수정 중이면 먼저 조정한다. 검증 도중 변경을 발견하면 해당 실행을 최종 검증으로 사용하지 않는다. Git 커밋은 검증된 작업 단위로 남기고 `reset --hard`로 사용자 변경을 정리하지 않는다.

검토된 PDF 기초 개념 47개·관계 28개의 원본도 QUESTION_SCENARIOS.md의 15·16절이다. 정확한 이름 대응에만 적용하고 AI 분석/원문과 역할을 구분한다. 생성기는 해당 절을 읽어 content.js에 포함한다.
